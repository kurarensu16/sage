# Post Defense Implementation Roadmap - 2026-10-28

**Status:** Index only. All 7 plan docs are drafted and their designs were confirmed by the developer on 2026-10-29 (see each plan's "Decisions" section) — the only decision still open across all 7 plans is row 7's tutor model/provider choice, which blocks only that row's backend build step. No code, migration, or edge function exists for any of items 1-7 yet. Each numbered item below has its own dedicated workflow-plan doc in this folder; every file listed under any of those plans still requires its own per-file developer confirmation before it is created or edited, per `AGENTS.md`. See `POST_DEFENSE_IMPLEMENTATION_PHASING_2026-10-29.md` for the concrete build-phase breakdown to follow now that designs are confirmed.
**Scope:** This document is a build-order index, not a feature plan. It does not describe *what* to build — each linked plan does that — it only fixes *which order* to build in, so an agent (human or AI) works from one plan at a time instead of touching the database and codebase across multiple unrelated features at once.
**Trigger:** Post-Capstone-1-defense revision items (role separation, grading hardening, consultation/dispute process, infrastructure) discussed and scoped across this conversation, ahead of the next defense milestone — hence "pre-defense."

## How to use this document

1. Work **one row at a time**, top to bottom. Do not start row *N+1* until row *N* is built, tested, and recorded per `AGENTS.md` §4.
2. Before starting a row, read its linked plan doc in full. If that plan doc doesn't exist yet, it needs to be drafted and reviewed before any code is touched for that row.
3. Update the **Status** column in this table as work progresses (`Not started` → `Drafted` → `In review` → `Approved` → `In progress` → `Done`). This file is the single place to check "what's next."
4. If a dependency isn't actually satisfied when you reach a row (e.g. the Registrar role isn't fully working yet), stop and fix the dependency first — do not route around it by building the dependent feature against a shortcut.

## Plans drafted and confirmed (2026-10-29)

All 7 plans are drafted, each including a "Current Setup vs. New Setup" section contrasting today's flow against the proposed one, and each plan's open decisions were walked through with the developer one at a time on 2026-10-29 — see every plan's own "Decisions" section for the full resolution list. Build order should still follow the same 1-7 sequence above, since later plans assume earlier ones land as designed (e.g. row 4 assumes the Registrar role from row 1 exists; row 6 assumes the Finalized state from row 5 exists).

The two cross-plan open decisions that surfaced during drafting are now resolved:

- **Unit-load cap** (row 4's Load Summary) — no cap added; Tab 1 displays totals informationally only, no over-limit flag.
- **R2 vs. Supabase Storage scope** (rows 2 and 6) — resolved as: Cloudflare R2 is adopted **only** for Grade Change Request evidence uploads (row 6), accessed via server-side signed URLs minted by an edge function. It never replaces or touches the existing `avatars` bucket, which stays on Supabase Storage permanently.

The one decision still open across all 7 plans is row 7's (AI Study Tutor) model/provider choice for `invoke-study-tutor` — the developer has ruled out reusing the OpenRouter fallback chain but hasn't finalized the replacement yet. This blocks only that row's backend edge-function step; nothing else in the 7-row sequence depends on it.
