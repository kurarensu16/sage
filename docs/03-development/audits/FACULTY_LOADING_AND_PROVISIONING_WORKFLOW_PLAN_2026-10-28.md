# Faculty Loading & Provisioning Workflow Plan - 2026-10-28

**Status:** Proposed design. No code or migration exists yet. Every file listed under "Suggested build order" still requires its own developer confirmation before it is created or edited, per `AGENTS.md`.
**Scope:** Reorganizes the existing single-step "pick subject + section + faculty, create" provisioning flow (`provisionClassroomByAdmin`) into one unified page shared by Registrar (all colleges) and Dean (own college only), adds a load-summary view, a per-college concurrency lock, and a no-join-code manual roster-add for irregular/off-block students. **Revised 2026-10-28 (second revision):** faculty loading now runs through an explicit **Draft -> Finalize** checkpoint, and assignment itself is a **cascading, faculty-first picker** (Faculty -> Program -> Year Level -> Class -> Add, repeatable) rather than a flat grid or a bulk spreadsheet import. **Bulk Excel/CSV import is explicitly dropped from this plan** — manually typed college/program/section values in a spreadsheet were judged too error-prone, so there is no import path at all; Excel is **export-only**, a one-way record/report of a college's faculty loads, never re-ingested. A class already assigned (drafted or finalized) to a faculty member is **hidden outright** from the Class step of the picker for every other faculty — collisions are prevented structurally, not caught after the fact. Does **not** touch the regular, join-code-based student self-join flow (`class_join_requests`, Faculty's Enrollment Requests) — that keeps working exactly as it does today, for regular students only.
**Trigger:** Capstone defense panel items 2.1, 2.4, and 2.5 — separating Admin/Registrar, clarifying who assigns subjects to faculty ("faculty loading"), and who opens subjects during an active term. Discussed and scoped across this conversation; the draft/finalize checkpoint was added after confirming the system has no class schedule/meeting-time data to check for true time conflicts. A bulk Excel-import design (with dropdown data validation, then with a Ready/Existing/Error/Override pattern mirroring Import Users) was explored and then explicitly rejected in favor of the simpler cascading-picker-with-hiding approach, on the grounds that manually typed spreadsheet values for college/program/section are too error-prone regardless of import-time validation.

## Objective

1. Separate "assign faculty to a subject+section" (**draft**) from "create the live class" (**finalize**) into two explicit steps, so Registrar/Dean can review a batch of assignments before any of them go live. `provisionClassroomByAdmin` is still reused verbatim — it now fires at Finalize time instead of at Assign time.
2. Give Registrar (all colleges) and Dean (own college) a shared, reorganized UI: a Load Summary panel (showing draft + live load together, with an Export action) and a **cascading, faculty-first Assignment picker** — Faculty -> Program -> Year Level -> Class -> Add, repeatable for the same faculty — instead of today's flat one-row-at-a-time modal.
3. **Prevent double-assignment structurally, not by catching it after the fact**: once a Program+Year Level+Class slot has any draft or finalized assignment, that Class option is **hidden** from the picker for every other faculty — a collision through this UI is not possible, so no bulk-import duplicate-check, Existing/Error preview, or Override toggle is needed. (Bulk Excel import itself is dropped from this plan entirely — see Scope.)
4. Prevent Registrar and Dean from editing the same college's assignments at the same time, with a visible "who's editing this" banner — this remains necessary even with hide-on-assign, since the hide rule is evaluated against the database at render/click time and two sessions open at once could each be looking at a page rendered before the other's most recent Add.
5. Remove Faculty's own provisioning entry point (`FacultyCreateClassroomModal.jsx`, `provisionBatchClassroomsByFaculty`) — Faculty keeps **My Classes** (view) and **Enrollment Requests** (approve/reject regular join-code requests), but can no longer create a class.
6. Add a no-join-code way for Registrar/Dean to put a specific irregular or off-block student directly on a specific (already-finalized) class roster, without disturbing the existing join-code path that regular students and today's irregular self-joiners already use.

## Why no automated conflict detection

The scenario that motivated the draft stage — "a faculty member could be assigned to different sections of the same class, and other conflict scenarios" — was checked against the actual schema: **`class_records` has no day/time/meeting-schedule field anywhere**, and no table in this codebase tracks class timetables (confirmed by grepping `schedule`/`time_slot`/`meeting_time` across `supabase/migrations` — the only hits are faculty consultation-appointment scheduling and notification delivery timing, both unrelated). A faculty member teaching the same subject across two different sections (e.g. ITC113 for both BSIT-1A and BSIT-1B) is normal, not a conflict — the only real conflict would be two assignments whose *meeting times* overlap, which isn't checkable without first adding a schedule field, a materially bigger change than this plan covers. So the draft stage's value here is **a human review checkpoint, not an automated schedule check**. The one thing the system *can* enforce automatically is that a given Program+Year Level+Class slot has at most one claimant — which this plan now does structurally, by hiding an already-assigned Class from the picker entirely (see "Design" below), rather than letting a second person pick it and then catching the collision afterward.

## Design: one page, two scopes, two tabs

Route: new `src/pages/registrar/FacultyLoadingAndProvisioning.jsx`, reused by Dean at `src/pages/dean/FacultyLoadingAndProvisioning.jsx` (or one shared component mounted at two routes — developer's call at build time) — scope is resolved from the logged-in role exactly like `ClassroomProvisioning.jsx` already resolves department filters today.

### Scope selector (top bar)
- **Registrar:** a college/department dropdown (same `departments` table `ClassroomProvisioning.jsx` already queries), defaulting to none selected.
- **Dean:** no dropdown — scope is fixed to `profile.department_id`, shown as a label only.
- Term picker, defaulting to the active `academic_terms` row, same as today.

### New table: `faculty_load_drafts`

```sql
CREATE TABLE public.faculty_load_drafts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  department_id UUID NOT NULL REFERENCES public.departments(department_id),
  subject_id UUID NOT NULL REFERENCES public.subjects(subject_id),
  section_id UUID NOT NULL REFERENCES public.sections(section_id),
  faculty_id UUID NOT NULL REFERENCES public.users(user_id),
  school_year TEXT NOT NULL,
  semester TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft', 'finalized', 'superseded')),
  class_record_id UUID NULL REFERENCES public.class_records(class_record_id),
  created_by UUID NOT NULL REFERENCES public.users(user_id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  finalized_by UUID NULL REFERENCES public.users(user_id),
  finalized_at TIMESTAMPTZ NULL,
  UNIQUE (subject_id, section_id, school_year, semester) -- only one non-superseded row per slot; enforced via a partial index excluding status = 'superseded'
);
```

A row starts as `draft`. Finalizing it calls `provisionClassroomByAdmin()` (unchanged), stamps `class_record_id`, `finalized_by`, `finalized_at`, and flips `status` to `finalized`. Reassigning an already-finalized slot via the explicit **Reassign** action (see "Reassigning an already-assigned class" below) does **not** touch the live `class_records` row's history — it updates `class_records.faculty_id` directly (a plain `UPDATE`, no re-provisioning) and the old draft row stays as the historical record of who originally loaded it, while the current faculty is whatever `class_records.faculty_id` now says. Draft rows are never hard-deleted — replacing one (via Reassign, or via an explicit "change faculty" edit before finalizing) flips the old row to `superseded` and inserts a new one, same archival-not-deletion philosophy used elsewhere in this codebase (e.g. the AI Study Tutor plan's plan-renewal flow).

### Tab 1 — Load Summary (new)
One row per faculty member in scope: name, sum of `subjects.units` across **both** their already-`finalized` `class_records` rows this term **and** their still-`draft` `faculty_load_drafts` rows, with a chip per subject/section distinguishing Draft from Open so the reviewer sees the complete picture — including work not yet live — before anything is finalized. No unit cap exists anywhere in the current schema (`subjects.units` is informational only) — flagged under Open Decisions below, since "flag faculty over a cap" needs a cap to compare against. An **Export** button here downloads that college's full load (draft + finalized) as an `.xlsx`, reusing `UserList.jsx`'s existing `XLSX.utils.json_to_sheet` / `XLSX.writeFile` pattern — no new dependency, no import counterpart, record-keeping only.

### Tab 2 — Assignment (cascading, faculty-first picker, draft then finalize)
Replaces the flat subject-by-subject grid with a sequence centered on one faculty member at a time:
1. **Pick Faculty** — search/select from faculty belonging to the selected college/department.
2. **Pick Program** — scoped to that college (`programs` filtered by `department_id`).
3. **Pick Year Level** — scoped to that program (whatever year levels that program's sections span).
4. **Pick Class** — the subject+section combinations available for that program+year level, this term, **with one exclusion: a Class that already has a draft or finalized `faculty_load_drafts`/`class_records` row for this term is left out of the list entirely.** It is not shown grayed-out, not shown with a warning — it simply is not an option, for any faculty other than the one it's already assigned to. This is what makes a double-assignment structurally impossible through this picker, rather than something caught after submission.
5. **Add** — inserts a `faculty_load_drafts` row (`status = 'draft'`) for the selected faculty+subject+section+term, then resets the picker back to step 2 (Program) so the *same* faculty's next subject can be added immediately: Program -> Year Level -> Class -> Add, repeated as many times as that faculty is being loaded this session, before moving on to a different faculty.
Each already-drafted/finalized row for the currently-selected faculty is listed below the picker as a running tally (mirroring Tab 1's per-faculty chips, scoped to just this one person) with its own **Finalize** action, plus a page-level **"Finalize All Drafts"** button for committing everything staged this session at once. Finalize calls `provisionClassroomByAdmin()` unchanged and stamps the draft row `finalized`. Nothing is visible to students, Enrollment Requests, or any other role until a row is Finalized — a Draft is purely a Registrar/Dean-side planning artifact.

### Reassigning an already-assigned class (separate, deliberate action — not part of the Add picker)
The hide-on-assign rule in step 4 above stops a *second* person from accidentally picking a slot that's taken, but a legitimate need remains: swapping the faculty on a class that's already drafted or finalized (e.g. the original faculty withdraws). This is **not** exposed through the Add picker — instead, an already-assigned row (visible in Tab 1's chips or Tab 2's per-faculty tally) carries its own explicit **"Reassign"** action: opens a small dialog to pick a *different* faculty for that exact existing row. Reassigning a still-`draft` row just updates `faculty_load_drafts.faculty_id` in place. Reassigning an already-`finalized` row updates `class_records.faculty_id` directly — no re-provisioning, no effect on existing enrollments — and the prior draft record is marked `superseded` with a new row capturing the change, per the archival-not-deletion rule below. This keeps "can't accidentally double-book a slot" (hidden from Add) and "can deliberately swap who's teaching it" (an explicit Reassign action on the existing row) as two separate, unambiguous operations instead of one overloaded control.

### Add Irregular Student to Class (action, not a tab — lives on an opened class's roster view)
A new button on a class's roster (reachable from Tab 2 once a row shows "Open") lets Registrar (any college) or Dean (own college) search a student by name/number and add them directly to that class's `enrollments` row — no join code, no `class_join_requests` row, no faculty approval step. `getEnrollmentType(student.section_id, class.section_id)` is called immediately after to label the new enrollment Regular or Irregular on the roster, reusing existing logic. This is additive only: students who still have a join code and want to self-request keep using Faculty's Enrollment Requests exactly as before; this button is for the cases that path was never meant to cover (an off-block elective, a block-sectioned student taking one extra subject, etc.).

## Per-college concurrency lock (new)

No presence/locking mechanism exists anywhere in the codebase today (`supabase.channel()` is used once, in `AtRiskStudents.jsx`, for a `postgres_changes` listener, not for presence) — this is a plain table plus RPC, consistent with how the rest of the app already works.

**New table** `provisioning_locks`:
```sql
CREATE TABLE public.provisioning_locks (
  department_id UUID PRIMARY KEY REFERENCES public.departments(department_id),
  locked_by UUID NOT NULL REFERENCES public.users(user_id),
  locked_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_heartbeat_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
- **Acquire** (`acquire_provisioning_lock(p_department_id)`): insert, or take over if `last_heartbeat_at` is older than the TTL (**3 minutes**). Returns the current holder's name either way, so the UI can show the read-only banner immediately on a failed acquire.
- **Heartbeat**: while the page stays open and scoped to that college, the client calls `touch_provisioning_lock(p_department_id)` every 60 seconds to refresh `last_heartbeat_at`. Stop on unmount/navigation-away, which lets the lock expire naturally within the 3-minute TTL instead of needing an explicit release call (covers browser-closed/crash cases that an explicit "release" button can't).
- **Release**: an explicit `release_provisioning_lock(p_department_id)` call on clean unmount (switching colleges, navigating away, logging out), for the common case of a fast handoff without waiting out the TTL.
- **Banner**: if acquire fails because someone else holds it, the page renders read-only — Tab 2's Add/Finalize picker and the Reassign action are disabled — with: *"[Registrar name] is currently editing [COLLEGE] — view only."* Tab 1 (Load Summary, including Export) stays visible either way since it's read-only by nature.

## Worked example

1. **Monday, 9:00 AM** — Registrar opens Faculty Loading & Provisioning, selects **College of Computer Studies**. `acquire_provisioning_lock('CCS')` succeeds. In Tab 2, Registrar picks **Faculty: Prof. Rivera**, then **Program: BSIT -> Year Level: 1st Year -> Class: ITC113 (BSIT-1A)**, clicks **Add** — a `faculty_load_drafts` row is inserted, `status = 'draft'`, **no live class yet.** The picker resets to Program; Registrar repeats Program -> Year Level -> Class -> Add four more times for Prof. Rivera's remaining subjects, building up all 5 of Rivera's assignments in one sitting.
2. **Monday, 9:02 AM** — The CCS Dean opens the same page, scope fixed to CCS. `acquire_provisioning_lock('CCS')` fails (Registrar's `last_heartbeat_at` is 2 minutes old, under the 3-minute TTL). Dean sees: *"Registrar J. dela Cruz is currently editing College of Computer Studies — view only."* Dean can still see Tab 1's Load Summary — which already shows Prof. Rivera's 5 Draft chips — but cannot assign, Finalize, or Reassign anything.
3. **Monday, 9:03 AM, same session** — Registrar switches to **Faculty: Prof. Santos**, picks **Program: BSIT -> Year Level: 1st Year**, opens the Class step — **ITC113 (BSIT-1A) is not in the list**, because it's already drafted to Prof. Rivera. There is nothing to collide with; Registrar simply picks a different class for Santos.
4. **Monday, 9:10 AM** — Registrar reviews Tab 1's Load Summary to confirm no one is overloaded, clicks **Finalize All Drafts**. Each row's `provisionClassroomByAdmin()` fires, both faculty members' classes go live, and the draft rows flip to `finalized`. Registrar exports an `.xlsx` of CCS's full load for the Dean's office's records, then navigates away; `release_provisioning_lock('CCS')` fires on unmount.
5. **Monday, 2:00 PM** — The CCS Dean reopens the page (lock now free) and realizes Prof. Rivera has actually withdrawn from ITC113 (BSIT-1A) and Prof. Santos needs to take over. Dean does **not** try to re-add it through the picker (it still wouldn't appear there, correctly). Instead, Dean finds that row in Tab 1's chip list and uses its **Reassign** action: picks Prof. Santos as the replacement. `class_records.faculty_id` updates directly — no re-provisioning, no effect on the students already enrolled — and the original draft row is marked `superseded` with a new row recording the change.
6. **Tuesday** — Dean adds a block-sectioned CCS student who also needs an off-block Math elective, using **Add Irregular Student to Class** on that already-finalized Math section's roster — no join code involved, and `getEnrollmentType` immediately labels the new row "Irregular" since the student's home section differs from the Math class's section.
7. **Meanwhile**, a regular BSIT-1A student who missed the auto-enrollment window (enrolled late) still goes through the normal join-code flow: gets the code from a classmate, submits it via `submitJoinRequest`, and Prof. Santos (per step 5's reassignment) approves it from **Enrollment Requests** exactly as today — this path never touches the Registrar/Dean page at all.

## Open decisions (confirm before any file is touched)

1. **Unit load cap**: no cap currently exists in the schema. Should Tab 1 just display totals with no flagging (informational only), or should a cap be added (e.g. a new `max_units` column on `users` or a fixed institutional constant) so "over-limit" can actually be flagged red?
2. **Shared component vs. two pages**: should Registrar and Dean literally share one React component mounted at two routes (scope resolved from role), or should they be two separate page files that both call the same underlying service functions? Affects how much of `ClassroomProvisioning.jsx` gets moved vs. duplicated.
3. **Lock TTL**: 3 minutes with a 60-second heartbeat is this plan's default — confirm or adjust.
4. **`FacultyCreateClassroomModal.jsx` deletion**: confirm it's safe to delete the file and its two service exports outright, rather than leaving them dead/unreachable, since nothing else in the codebase calls `provisionClassroomByFaculty` or `provisionBatchClassroomsByFaculty` except this modal (grep confirms both are only referenced from this one file).
5. **Finalize granularity**: is a per-row Finalize button sufficient, or is the batch **"Finalize All Drafts"** button (used in the worked example) a hard requirement for launch? Affects whether Finalize needs its own confirm-modal summarizing everything about to go live at once.
6. **Reassign permissions**: should the Reassign action (on an already-assigned row) be available to both Registrar (any college) and Dean (own college) equally, same as the Add picker, or should reassigning an already-*finalized* class require an extra confirmation step given students may already be attending under the original faculty?
7. **Notifying the reassigned/replaced faculty**: when Reassign swaps a class's faculty (draft or finalized), should the old and new faculty members get a notification (existing `notificationService.js` pattern), or is this silent/audit-log-only? Given a faculty member could otherwise discover they've been added to or removed from a class with no warning, a notification seems warranted but isn't yet in this plan's scope.
8. **Export file scope and timing**: does Export capture a live snapshot at click-time only (no history), and does it include already-`superseded` draft rows (full history) or only the current state of each slot? Affects how useful it is as a "record" versus a point-in-time report.

## Suggested build order

1. Migration: `provisioning_locks` table (lock RPCs), `faculty_load_drafts` table (status enum, unique-per-slot partial index, Finalize/Reassign marking columns) — developer applies manually.
2. New shared page (or two role-scoped pages): scope selector, Tab 1 Load Summary (read-only query against `class_records` + `faculty_load_drafts` + `subjects.units`, plus the Export button reusing `UserList.jsx`'s `XLSX` pattern).
3.
